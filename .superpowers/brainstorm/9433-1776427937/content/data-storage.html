Где хранить данные запросов и голосов?

Это ключевое архитектурное решение — влияет на всё остальное

A

Bitrix24 Entity Storage

Данные живут в самом Bitrix24 через REST API (entity.item.add, entity.item.get). Как написано в спецификации проекта.

Плюсы

  • Нет своей БД — проще инфраструктура
  • Данные в Bitrix24 — доступны из CRM
  • Меньше кода на бэкенде
  • Соответствует оригинальной спеке

Минусы

  • Лимиты на запросы к API
  • Нет сложных JOIN-запросов
  • Зависимость от Bitrix24
B

PostgreSQL (своя база)

Данные в PostgreSQL через Django ORM. Bitrix24 используется только для бота и кнопок. В docker-compose уже есть.

Плюсы

  • Полная мощь SQL и транзакций
  • Решает race conditions при голосовании
  • Быстрые запросы, сложная аналитика
  • Независимость от лимитов API

Минусы

  • Своя инфраструктура (PostgreSQL)
  • Больше кода (модели, миграции)
  • Данные вне Bitrix24
C

Гибрид

PostgreSQL как основное хранилище + синхронизация с Bitrix24 entity для видимости внутри CRM.

Плюсы

  • Лучшее из двух миров
  • Надёжность + видимость в CRM

Минусы

  • Двойная логика синхронизации
  • Сложнее отлаживать
  • Избыточно для MVP
Мой совет

Вариант B (PostgreSQL) — правильный выбор для продакшена. Race conditions при одновременных голосах — реальная проблема. SELECT FOR UPDATE в Django решает это элегантно. Entity storage не даёт транзакций.
