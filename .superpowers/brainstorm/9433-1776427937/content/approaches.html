Архитектура системы — 3 подхода

Выберите подход перед проектированием деталей

A

Фронт-тяжёлый (через B24 JS SDK)

Фронтенд напрямую вызывает Bitrix24 REST. Django только обрабатывает входящие webhook-события от кнопок бота.

Nuxt → B24 JS SDK → entity.item.add / imbot.message.add
Bitrix24 кнопка → webhook → Django → валидация → entity.item.update

Плюсы

  • Меньше кода на бэкенде
  • Быстрее разработка
  • SDK берёт авторизацию на себя

Минусы

  • Бизнес-логика размазана по фронту и беку
  • Сложнее тестировать
  • Токены B24 видны клиенту
B

Бэк-тяжёлый (Django как API)

Фронт обращается только к Django. Django хранит B24-токены на сервере и сам вызывает Bitrix24 REST. Единственная точка правды.

Nuxt → POST /api/approval/create → Django → B24 REST
Bitrix24 кнопка → webhook → Django → правила → B24 REST

Плюсы

  • Вся бизнес-логика в одном месте
  • Легко тестировать (unit tests)
  • Безопаснее — токены на сервере
  • Проще добавлять правила позже

Минусы

  • Больше кода изначально
  • Все запросы через бэк
C

Гибрид (чтение на фронте, запись через бэк)

Фронт читает данные напрямую из B24 (entity.item.list). Все мутации — через Django (создать, голосовать, отменить).

Nuxt → B24 JS SDK → entity.item.list (чтение)
Nuxt → POST /api/approval/create → Django (запись)
Bitrix24 кнопка → webhook → Django → правила

Плюсы

  • Быстрое чтение без лишнего слоя
  • Правила и мутации централизованы
  • Разумный баланс

Минусы

  • Два пути к данным — сложнее дебажить
  • Надо синхронизировать права доступа
Мой совет

Вариант B — правильный для приложения с бизнес-правилами. Вся логика в Django: порог одобрения, защита от двойного голоса, мгновенный отказ. Тестируется изолированно. Фронт — тонкий клиент.
