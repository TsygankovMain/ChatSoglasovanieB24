# Справочник REST API

*Состояние на 02.10.2026. Описывает то, что есть в коде `backends/python/api`.*

Бэкенд не хранит состояния: у него нет базы данных и нет сохранённых токенов порталов. Каждый запрос приносит авторизацию с собой, а данные согласований лежат в хранилище самого портала (см. [DATABASE.md](DATABASE.md)).

## Авторизация

Интерфейс получает у Битрикс24 OAuth-токен текущего пользователя и один раз обменивает его на JWT. Дальше все запросы идут с заголовком `Authorization: Bearer <JWT>`.

### POST /api/getToken

Тело — данные авторизации из фрейма Битрикс24:

```json
{
  "DOMAIN": "portal.bitrix24.ru",
  "AUTH_ID": "<access_token>",
  "REFRESH_ID": "<refresh_token>",
  "AUTH_EXPIRES": 3600,
  "member_id": "<member_id>"
}
```

Ответ: `{"token": "<JWT>"}`. JWT живёт 60 минут.

Перед выдачей JWT бэкенд спрашивает у портала методом `profile`, кому принадлежит токен. Идентификатор пользователя и признак администратора берутся только из этого ответа; поле `user_id` из тела запроса не учитывается. Если портал токен не подтвердил — `401`.

Домен портала проверяется по формату: допускается только имя хоста (с необязательным портом), IP-адреса и `localhost` отклоняются.

## Запросы согласования

### POST /api/approval/create

`multipart/form-data`:

| Поле | Обязательное | Описание |
|---|---|---|
| `comment` | да | Текст запроса, до 4000 символов |
| `approver_ids` | да | JSON-массив идентификаторов пользователей, от 1 до 10. Повторы убираются. Инициатор в список входить не может |
| `threshold_type` | да | `all` — единогласно, `majority` — большинство |
| `dialog_id` | да | Чат, из которого создан запрос |
| `files` | нет | До 10 файлов, каждый до 25 МиБ; разрешённые расширения — в `approvals/serializers.py` |

Ответ `201`:

```json
{
  "id": "42",
  "status": "collecting",
  "bot_message_ids": ["1001", "1002"],
  "bot_dialog_ids": ["7", "12"],
  "bot_issue": ""
}
```

`bot_issue` непустой, если бот не смог доставить сообщение кому-то из согласующих: запрос создан, но часть людей о нём не узнала.

Ошибки проверки — `400` с текстом в поле `error`.

### GET /api/approval/list

Параметры:

| Параметр | По умолчанию | Описание |
|---|---|---|
| `role` | `initiator` | `initiator` — мои запросы, `approver` — входящие |
| `offset` | `0` | Сколько записей пропустить |
| `limit` | `20` | Размер страницы, не больше 50 |

Ответ:

```json
{
  "items": [ { "id": "42", "status": "collecting", "votes": [], "approver_names": {} } ],
  "has_more": true,
  "offset": 0,
  "limit": 20
}
```

Записи идут от новых к старым. В списке у запроса есть голоса и имена, но нет журнала событий и ссылок на файлы — они приходят в подробной карточке.

Для роли `approver` просматриваются последние 1000 запросов портала: в хранилище Битрикс24 нет поиска по вхождению в список согласующих.

### GET /api/approval/{id}

Полная карточка: голоса, журнал событий (`events`), файлы со ссылками (`files`). Доступна инициатору, согласующим и администратору портала, остальным — `403`.

### POST /api/approval/cancel

Тело: `{"request_id": "42"}`. Отменить может только инициатор и только незавершённый запрос. Ответ: `{"id": "42", "status": "cancelled"}`.

## Голосование

Голосуют не через интерфейс, а кнопками в сообщении бота. Битрикс24 присылает событие `ONIMCOMMANDADD` на `POST /api/vote/handle`.

Событие не подписано, поэтому идентификатор голосующего в нём — только заявление. Бэкенд берёт токен из блока `auth` события (это авторизация нажавшего кнопку), спрашивает у портала, чей он, и принимает голос, только если владелец токена совпал с голосующим. Иначе — `401`.

Дальше действуют правила из `approvals/rules.py`:

- голосовать может только согласующий по этому запросу; инициатор не голосует;
- один человек голосует один раз, изменить решение нельзя;
- по завершённому запросу голоса не принимаются.

Итог запроса:

| Правило | Одобрено | Отклонено |
|---|---|---|
| Единогласно (`all`) | согласовали все | отклонил хотя бы один |
| Большинство (`majority`) | согласовали больше половины | согласовать больше половины уже невозможно |

Пример для трёх согласующих при правиле «Большинство»: нужны два голоса «за». Один отказ запрос не закрывает, два отказа — закрывают.

## Служебные

| Метод | Назначение |
|---|---|
| `POST /api/install` | Установка: хранилища, бот, команды кнопок, три встройки в чат. Вызывается мастером установки |
| `POST /api/event/onAppUninstall` | Подтверждение события удаления приложения; чистить на бэкенде нечего |
| `GET /api/health` | Проверка бэкенда из интерфейса, требует JWT |
| `GET /nginx-health` | Проверка контейнера, без авторизации |

## Коды ответов

| Код | Когда |
|---|---|
| `200`, `201` | Успех |
| `400` | Не прошла проверка формы или правил |
| `401` | Нет или истёк JWT; портал не подтвердил токен |
| `403` | Нет прав на запрос |
| `404` | Запрос не найден |
| `413`, `415` | Файл слишком большой или запрещённого типа |
| `500` | Ошибка. Текст ответа Битрикс24 отдаётся как есть, внутренние ошибки — без подробностей, подробности в журнале |

Ошибка всегда приходит как `{"error": "<текст>"}`.
